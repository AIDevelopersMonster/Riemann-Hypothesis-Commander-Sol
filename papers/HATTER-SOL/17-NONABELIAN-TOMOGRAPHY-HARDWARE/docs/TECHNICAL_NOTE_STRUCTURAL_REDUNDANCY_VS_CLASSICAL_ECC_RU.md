# HATTER-SOL-17 · Техническая заметка
## Структурная избыточность H17 и классические самовосстанавливающиеся коды

**Статус:** инженерная интерпретация уже доказанных H17-04/H17-06/H17-08 результатов.  
**Назначение:** зафиксировать, в чём H17 действительно отличается от классических ECC/erasure codes, где у него может быть практическое преимущество и где такого преимущества утверждать нельзя.

---

## 1. Краткий вывод

H17 в текущем виде **не является универсальным кодом коррекции ошибок и не претендует на превосходство над Hamming, BCH, Reed-Solomon или другими классическими ECC** при передаче произвольных данных.

Его особенность другая:

> избыточность возникает не как отдельно добавленные parity-биты, а как следствие самой структуры наблюдаемого математического объекта.

Для H17 robust8 один generating-state представлен восемью связанными наблюдениями

[
F(A,B)=(c_0,ldots,c_7),
]

где каждая координата — класс одного из восьми фиксированных групповых слов.

Используемая observer family:

[
oxed{
AAB, Abb, AAAB, Abbb, AABAb, AAbAb, ABABB, ABaBB
}
]

На 114 generating simultaneous-conjugacy orbits эти fingerprints различны. Более того, при известном положении одного стирания проекция на оставшиеся семь координат всё ещё однозначно определяет generating orbit; H17-06 даёт ROM-free repair network.

Следовательно, в H17 одно и то же описание объекта одновременно играет три роли:

1. **идентификация структурного состояния**;
2. **проверка принадлежности допустимому классу состояний**;
3. **восстановление одной известной стёртой координаты**.

Это и есть основное отличие от схемы «payload + отдельно добавленный ECC».

---

## 2. Что именно уже установлено в H17

Для текущего robust8-кода доказано и вычислительно сертифицировано:

- число generating simultaneous-conjugacy orbits: **114**;
- число observer coordinates: **8**;
- каждая координата принимает один из шести ориентированных классов
  [
  1A, 2A, 3A, 4A, 7A, 7B;
  ]
- аппаратная кодировка одной координаты занимает 3 бита;
- полный fingerprint занимает **24 бита**;
- generating fingerprints попарно различны;
- после удаления любой **одной известной** координаты generating projection остаётся однозначной;
- generating/non-generating separation сохраняется для одной известной erasure;
- ROM-free repair использует decision trees с worst-case глубиной не более 4 class queries;
- H17-08 позволяет не выполнять полную membership-проверку для каждого внутреннего слова: принадлежность производных слов следует из замкнутости группы после проверки исходных (A,B).

Эти утверждения относятся к конечному H17-домену. Они не означают автоматически коррекцию произвольной неизвестной ошибки, burst-error correction или кодирование произвольного битового потока.

---

## 3. Почему это не «Reed-Solomon лучше Reed-Solomon»

Если рассматривать только передачу абстрактного номера состояния, 114 состояний несут

[
log_2 114 approx 6.83
]

бит информации.

Практически такой state ID помещается в 7 бит.

H17 fingerprint занимает

[
8cdot 3=24
]

физических бита.

Если искусственно считать его обычным communication code, эффективная payload rate составляет приблизительно

[
R_{mathrm{H17}}
=
rac{log_2 114}{24}
approx 0.285.
]

То есть около 28.5%.

Для задачи «передать номер 0..113 через ненадёжный канал» стандартный специализированный код почти наверняка можно построить существенно компактнее.

Поэтому неверная постановка:

> H17 — более эффективный ECC для обычных данных.

Корректная постановка:

> H17 исследует ситуацию, когда структурные наблюдения, необходимые для классификации объекта, сами образуют erasure-resilient representation.

---

## 4. Где появляется потенциальное преимущество

Рассмотрим два разных инженерных сценария.

### 4.1. Payload уже дан как обычный state ID

Имеется:

[
sin{0,ldots,113}.
]

Нужно только надёжно передать (s).

Тогда естественная архитектура:

[
7	ext{-bit state ID}
longrightarrow
	ext{standard ECC}
longrightarrow
	ext{channel}.
]

В таком сценарии у H17 пока нет основания ожидать преимущества. Преобразовывать простой 7-битный ID в 24-битный групповой fingerprint только ради защиты обычно нерационально.

### 4.2. Состояние всё равно определяется структурными наблюдениями

Имеется объект ((A,B)), а для его распознавания уже вычисляются классы групповых слов.

Обычная архитектура может выглядеть так:

[
(A,B)
ightarrow
	ext{structural classification}
ightarrow
	ext{state ID}
ightarrow
	ext{ECC encoder}
ightarrow
	ext{protected state}.
]

H17 предлагает объединить слои:

[
(A,B)
ightarrow
	ext{robust structural observations}
ightarrow
oxed{
	ext{classification + admissibility + erasure repair}
}.
]

В этом случае дополнительный ECC-слой может оказаться частично или полностью избыточным, потому что коррекционное свойство уже встроено в representation.

Именно здесь H17 имеет инженерный смысл.

---

## 5. Концептуальное различие

### Классический ECC

[
	ext{payload}
ightarrow
	ext{encoder}
ightarrow
	ext{payload + engineered redundancy}.
]

Избыточность создаётся намеренно для защиты данных.

### H17 structural redundancy

[
	ext{structured object}
ightarrow
	ext{several correlated observations}.
]

Корреляции между наблюдениями существуют из-за математики самого объекта.

После выбора подходящей observer family оказывается, что эти корреляции достаточны для восстановления одного стирания:

[
(c_0,ldots,c_{j-1}, ?, c_{j+1},ldots,c_7)
longrightarrow
(c_0,ldots,c_7).
]

Поэтому рабочая формулировка принципа H17:

[
oxed{
	ext{не добавлять защиту к данным, если можно выбрать наблюдения так,}
\
	ext{чтобы само описание объекта уже было защищено своей структурой.}
}
]

---

## 6. Что H17 получает «одновременно»

Для допустимого generating state robust8 fingerprint является не просто кодовым словом.

Он несёт одновременно:

### 6.1. Идентичность состояния

Fingerprint различает 114 generating orbits.

### 6.2. Структурную допустимость

Не всякая произвольная 24-битная строка является H17 fingerprint.

Decoder работает на очень разреженном структурированном подмножестве пространства возможных слов.

### 6.3. Избыточность для known erasure

Любая одна известная coordinate может быть удалена без потери однозначной generating-state identification.

### 6.4. Возможность ROM-free decoding

H17-06 заменяет полный 114-entry orbit lookup decision network, которая восстанавливает fingerprint по surviving coordinates.

### 6.5. Возможность closure-aware hardware

H17-08 использует теорему о замкнутости PSL(2,7), чтобы не повторять полную membership logic для каждого производного слова.

Это важный пример того, как математическая теорема непосредственно удаляет аппаратную логику.

---

## 7. Где классические коды сильнее

Для инженерной честности необходимо явно зафиксировать ограничения H17.

Классические ECC имеют преимущества:

- кодируют **произвольный payload**;
- имеют развитую теорию code rate / distance / decoding;
- существуют семейства для single-bit, multi-bit, symbol и burst errors;
- доступны стандартные высокопроизводительные encoder/decoder IP;
- их поведение хорошо изучено на шумовых каналах;
- они не требуют групповой семантики исходных данных.

Текущий H17 robust8 гарантирует именно:

[
oxed{	ext{one known coordinate erasure}}
]

на фиксированном конечном структурном домене.

Он не должен описываться как universal ECC.

---

## 8. Почему всё-таки имеет смысл аппаратный эксперимент

Практический вопрос не решается сравнением формул code rate.

Нужно сравнивать две **end-to-end архитектуры**.

### Архитектура A — conventional

[
(A,B)
ightarrow
	ext{classifier}
ightarrow
7	ext{-bit state/orbit ID}
ightarrow
	ext{standard protection}
ightarrow
	ext{decoder}.
]

### Архитектура B — H17

[
(A,B)
ightarrow
	ext{closure-aware robust8 classifier}
ightarrow
24	ext{-bit structural fingerprint}
ightarrow
	ext{ROM-free repair}.
]

Сравнивать следует не только ширину передаваемого слова, а всю цену получения защищённого состояния.

---

## 9. Необходимый benchmark

Следующий инженерный этап должен содержать минимум два baseline.

### Baseline 1 — state ID already available

Вход уже является числом 0..113.

Это контрольный сценарий, в котором классический ECC должен иметь естественное преимущество.

Он показывает цену H17, если структурная семантика вообще не нужна.

### Baseline 2 — state must be inferred from ((A,B))

Входы совпадают с H17:

[
A[23:0],quad B[23:0].
]

Обе реализации должны выдать защищённую идентификацию одного и того же finite state.

Тогда сравниваются:

- LUT;
- FF;
- BRAM;
- DSP;
- maximum combinational depth / timing;
- clocks per transaction;
- throughput;
- recovery latency;
- decoder storage;
- power, если target flow позволяет получить честную оценку;
- типы отказов, которые гарантированно обнаруживаются/восстанавливаются.

Особенно важно разделять:

[
	ext{classification cost}
]

и

[
	ext{protection cost}.
]

Именно это покажет, действительно ли structural redundancy устраняет отдельный ECC layer или только переносит его стоимость в более сложный classifier.

---

## 10. Fairness rule

Сравнение должно явно фиксировать fault model.

H17 сегодня гарантирует **известное положение одной стёртой 3-битной coordinate**.

Поэтому нельзя сравнивать его с классическим decoder для намного более сильного fault model, а затем объявлять один подход «лучше».

Нужны отдельные строки:

| Fault model | H17 robust8 | Classical baseline |
|---|---:|---:|
| one known 3-bit symbol erasure | да | сравнить |
| one unknown symbol corruption | не установлено | зависит от кода |
| one bit error | не текущая спецификация | зависит от кода |
| multiple erasures | не текущая гарантия | зависит от кода |
| burst corruption | не текущая гарантия | зависит от кода |

Это делает будущий FPGA benchmark содержательным, а не рекламным.

## 11. Возможное изделие

Наиболее естественная продуктовая форма H17 — не файловый или сетевой ECC-кодек, а:

> **fault-tolerant finite-state / command processor для структурированных состояний.**

Например, блок с контрактом:

~~~text
structured input / state source
        |
        v
H17 observation/classification
        |
        +--> VALID
        +--> STATE
        +--> FINGERPRINT
        +--> ERASED_COORDINATE_REPAIRED
        +--> UNCORRECTABLE
~~~

В таком устройстве смысл H17 состоит не в экономии битов, а в объединении:

[
oxed{
	ext{распознавания}
+
	ext{валидации}
+
	ext{отказоустойчивого восстановления}
}
]

в одной математической representation.

---

## 12. Инженерный критерий успеха

H17 следует считать практически интересным относительно обычного решения только если хотя бы в одном реалистичном structural-state workload будет показано одно из следующего:

1. меньшая end-to-end аппаратная стоимость;
2. меньшая latency от структурного входа до восстановленного state;
3. отсутствие отдельного state-ROM / orbit-ROM;
4. более сильная семантическая validation при сравнимой стоимости;
5. удобная fault isolation на уровне физических observer channels;
6. выигрыш по верифицируемости: одна и та же математическая спецификация определяет classification и repair.

Если ничего из этого не подтвердится, результат всё равно остаётся содержательным:

> H17 будет примером математической томографии со встроенной структурной избыточностью, но не конкурентом специализированным communication ECC.

---

## 13. Итог

Главная инженерная гипотеза H17 не такова:

[
	ext{«мы построили код лучше Reed-Solomon».}
]

Она такова:

[
oxed{
	ext{можно ли спроектировать наблюдения структурного объекта так,}
\
	ext{чтобы они одновременно идентифицировали объект и сами}
\
	ext{обеспечивали отказоустойчивость без отдельного слоя ECC?}
}
]

H17 robust8 даёт конечный, полностью проверяемый положительный пример на уровне одной известной erasure.

Следующий шаг — не расширять этот тезис словами, а поставить честный аппаратный benchmark:

[
oxed{
	ext{structural H17 pipeline}
quad	ext{vs}quad
	ext{state classifier + conventional ECC}.
}
]

И только после этого можно говорить о реальном инженерном преимуществе.
